# Инструкции для агентов

Тренажёр собеседований: Node.js, TypeScript, `node:test`, локальный веб. Кто за что отвечает и чем подтверждается результат — `docs/workflow.md`. Этот файл — порядок действий, независимо от инструмента.

## Куда смотреть

- Трекер, метки, чтение домена: `docs/agents/`.
- Словарь: `GLOSSARY.md`. Решение: `docs/adr/`.
- Повторяемый сбой стека: `.cursor/rules/learned-cases.mdc`.

## Неизменные правила

- Сессия читает утверждённое досье, с которым её открыли (ADR-0001).
- Ход подготовки не становится материалом проекта (ADR-0002).
- Протокола два: родной Anthropic и совместимый с OpenAI (ADR-0003).
- Каталог владельца `data/`, секреты и `tmp/` в git не входят. Веб первой версии слушает машину владельца (ADR-0004).
- Имя из глоссария не заменять словом из его списка «избегать».
- Свой план в `.cursor/plans/` по просьбе человека обновлять можно. Чужой план не править.

## Задание «сделай issue N»

1. **Прочитать issue** так, как написано в `docs/agents/issue-tracker.md`. Спросить человека до кода, если нет критериев приёмки, они допускают два прочтения, задача меняет правило предметной области (нужен ADR или правка `GLOSSARY.md`) или изменение хранилища стирает проекты, досье, сессии или ключи. Для области docs отсутствие теста в `test/` само по себе не остановка: issue называет, чем проверить критерий. В остальных случаях работать без остановок.
2. **Ветка** `issue-<N>-<коротко>` от свежего `origin/master`. Коммиты — только в ветку задачи.

   **Разбиение** — до первой правки, если задача шире одного файла: таблица в `.cursor/plans/issue-<N>-split.md` (номер, блок, исполнитель `родитель` или `dsh`, чем проверяется).
   - dsh, когда доступен: разведка по пяти и более файлам, полный `npm run verify`, ревью diff перед pull request, механические массовые правки.
   - Родитель: глоссарий и ADR, смысл критериев, финальный гейт, ответы человеку.
   - Если dsh недоступен, родитель делает назначенные ему блоки и называет причину в отчёте (шаг 7).
3. **Реализация** — минимальная, в стиле соседнего кода.
4. **Тесты.** На каждый критерий — тест в `test/` (новый или правка существующего) либо проверка, которую назвал issue. Негативный случай обязателен. Для области docs достаточно проверки из issue.
5. **Проверки.** `npm run verify` до коммита. Пока правки идут одна за другой, достаточно `node --test test/<файл>.test.ts`. Упавшую проверку чинить. В таблицу pull request копировать вывод команд.
6. **Коммит, push, pull request.** Перед коммитом сверить diff со списком в `.cursor/agents/pr-review.md`. Описание — по `.github/pull_request_template.md`, строка `Closes #N`.
7. **Стоп.** Сообщить человеку ссылку на pull request и итог проверок. В отчёте — строка `Оркестрация: dsh <k> из <n> блоков` и причина, если назначенные dsh блоки сделал родитель. Дальше — ответы на ревью, правки, merge — только по запросу. Merge агент не делает.

## Ответ на ревью

По запросу человека: прочитать комментарии к pull request. Каждое замечание исправить или ответить отказом со ссылкой на ADR, глоссарий или правило. После правок — снова шаг 5, затем push в ту же ветку.

## Состояние долгой задачи

Задача переживает сжатие контекста, поэтому её состояние живёт в файле: `tmp/issue-<N>-state.md` (папка в git не попадает).

- Писать после разведки, после правок и после проверок.
- Разделы: ветка и pull request; что сделано; чем проверено (команда и результат); открытые замечания ревью с решением; что осталось.
- Новая сессия по той же задаче начинается с этого файла и `git status`.

## Уроки

Повторяемый сбой стека, подтверждённый логом, — пункт в `.cursor/rules/learned-cases.mdc`. Продуктовое решение — `GLOSSARY.md` или ADR.
